# Datasheet: BBO Capstone Project Dataset

This datasheet documents the dataset used for the Black-Box Optimization (BBO) capstone project at Imperial College London, following the framework from Mini-lesson 21.1. It draws on reflections from Required capstone component 21.1 and weekly diaries.

---

## 1. Motivation

**Why was this dataset created?**

The dataset was created to support a **course-based black-box optimization challenge**. The primary task is to **maximise the output** of eight unknown, expensive-to-evaluate functions with very limited queries (approximately one submission per function per week over 12 weeks, i.e. ~96 total evaluations across all functions).

**What task does it support?**

- **Optimization**: Finding input configurations that maximise each function’s scalar output.
- **Strategy learning**: Testing exploration vs exploitation, surrogate models (Gaussian processes, logistic regression, neural networks), and acquisition strategies (UCB, Expected Improvement, noise-aware BO).
- **Reproducibility and reflection**: Weekly inputs/outputs and notebooks support reviewing decisions, assumptions, and limitations (e.g. transparency of decision-making, as in week 10 reflections).

The data are not intended for training general-purpose ML models; they are **task-specific query–response pairs** for this optimisation challenge.

---

## 2. Composition

**What does the dataset contain?**

- **Eight black-box functions**, each with fixed dimensionality (2D to 8D). For each function:
  - **Inputs**: Continuous vectors in **[0, 1]^d** (d = 2, 2, 3, 4, 4, 5, 6, 8 for functions 1–8).
  - **Outputs**: A single scalar per query (maximisation; higher is better). Scales and noise levels differ across functions (e.g. some near zero, some in the thousands; Function 3 is explicitly noisy).

- **Initial data**: For each function, a set of initial (input, output) pairs is provided (e.g. `data/initial_data/function_1/` through `function_8/` with `initial_inputs.npy` and `initial_outputs.npy`).

- **Weekly submission data**: Each week, one new query per function is submitted. Results are stored in `data/weekN/` as `inputs.txt` and `outputs.txt`. Each file contains one list per function: 8 entries per week (one input array and one output value per function). Format is evaluable Python (e.g. `[array([...]), ...]` for inputs and corresponding scalar outputs).

**Size and format**

- **Size**: Grows each week. Per function, total observations = initial set size + number of weeks submitted (e.g. after 7 weeks, roughly 7–17+ points per function depending on initial set size).
- **Format**: 
  - Initial: NumPy `.npy` (arrays).
  - Weekly: Text files (`inputs.txt`, `outputs.txt`) with one line or block per function, parseable as Python lists/arrays.

**Gaps and caveats**

- **Spatial gaps**: Queries are chosen by optimisation strategies (exploration then exploitation), so the distribution of queries is **non-uniform** and can leave large regions of the input space unobserved. As noted in week 10 reflections, there are unexplored areas and potential sampling biases depending on where the strategy focused.
- **Temporal gaps**: One submission per function per week means no dense sampling in time; re-evaluating the same point (e.g. for noisy Function 3) uses extra weekly “slots” and is done only when needed.
- **Missing or partial data**: If a week is not submitted or files are incomplete, that week’s data may be missing for some functions. The loader uses the “latest” valid block in each file to support appended histories.

## 3. Collection Process

**How were the queries generated?**

Queries were generated by **surrogate-based optimisation strategies** chosen per function:

- **Function 1 (2D, sparse/near-binary behaviour)**: Non-linear logistic regression (polynomial features) to learn a decision boundary; next point chosen where P(good) ≈ 0.5 (maximum uncertainty). Hyperparameters (e.g. degree, threshold percentile, C) were tuned via grid search (see week 7 reflections).
- **Functions 2, 4, 5, 6**: Bayesian optimisation with a **Gaussian process (GP)** surrogate and **Upper Confidence Bound (UCB)** acquisition; exploitative variant (β = 0) to refine around promising regions. Where progress plateaued, **Expected Improvement (EI)** was used to better balance exploration and exploitation (week 10).
- **Function 3 (noisy)**: **Noise-aware BO** (GP with WhiteKernel, moderate β, local restarts near the incumbent) to handle stochastic outputs; same point was sometimes re-run to check consistency.
- **Functions 7 and 8 (6D, 8D)**: **Neural network surrogate** (PyTorch MLP) fitted to observed data; next point via **gradient-based optimisation** (multiple restarts) on the surrogate, with modest compute (e.g. 1200 epochs, 64 hidden units, 25 restarts) as in week 9 reflections.

**Strategy over time**

- **Weeks 1–3**: Exploration — diverse sampling to build surrogates.
- **Weeks 4–6**: Transition — more exploitation, progress validation, and method-specific tuning (e.g. noise-aware BO for Function 3).
- **Weeks 7–10**: Exploitation and refinement — focus on promising regions; EI used when exploitative BO did not improve (week 10).

**Time frame**

- The challenge runs over **14 weeks**, with roughly **one query per function per week** (~14 evaluations per function in total).

## 4. Preprocessing and Uses

**Transformations**

- **Loading**: Raw text files are parsed (e.g. via `eval` with restricted namespaces) or NumPy load for `.npy`. The code in `scripts/utils/data_utils.py` combines initial and weekly data (e.g. `load_initial_data`, `load_week1_data`, …, `_load_latest_week_data`) and can stack observations per function for surrogate fitting.
- **Scaling**: Inputs are already in [0, 1]. Some pipelines (e.g. neural network) normalise outputs (e.g. mean/std) for training; predictions are then de-normalised.
- **Binarisation (Function 1)**: Outputs are turned into binary labels (e.g. “good” if above a percentile threshold) for logistic regression; threshold and degree are tuned.

**Intended uses**

- Running and reproducing the BBO strategy (e.g. re-fitting surrogates, suggesting next points).
- Analysing strategy choices, progress over weeks, and impact of method changes (e.g. EI vs exploitative BO, noise-aware BO).
- Educational and reflective use: understanding exploration/exploitation, surrogate choice, and limitations (see weekly diaries and model card).

**Inappropriate uses**

- **General-purpose model training**: The data are small, non-i.i.d., and tied to specific black-box functions; they are not representative of a broader distribution and should not be used to train models for deployment on other tasks.
- **Benchmarking other algorithms without caveats**: Query locations are strategy-dependent; comparing algorithms would require fixed evaluation protocols or new runs, not reusing this dataset as a static benchmark.
- **Inference about the true functions**: The functions are unknown; the dataset only records (input, output) pairs and may contain noise (e.g. Function 3). Any conclusions about function shape or global optima are limited by sampling and noise.

## 5. Distribution and Maintenance

**Where is the dataset available?**

- **Repository**: The dataset is stored in the project’s GitHub repository under `data/`:  
  - `data/initial_data/function_1/` … `function_8/` (initial_inputs.npy, initial_outputs.npy),  
  - `data/week1/` … `data/week7/` (and later weeks as submitted) with `inputs.txt` and `outputs.txt`.
- **Access**: The repository is public so that peers and facilitators can view and use the data and link from the README (see Part 3).

**Terms of use**

- The data are part of an academic capstone project. Use should respect Imperial College London and the course’s academic integrity and attribution expectations. No separate licence file is specified; default is repository/owner terms.

**Maintenance**

- **Maintainer**: The capstone author (Jack Dunning) maintains the repository.
- **Updates**: Weekly data are added as new submissions are made (each new week’s inputs and outputs appended or added under `data/weekN/`). The datasheet and README should be updated if the structure or collection process changes significantly.
